# LoRA Training Plan: Macro-Aware Coding Model

**Goal:** Fine-tune an open-weight model to natively use `@{VAR}` macro syntax in
bash tool calls — zero prompt overhead, ~54% theoretical input token reduction on
agentic coding sessions.

**Status:** Planning. Eval complete, model selected, training data design TBD.

---

## Context

The macro compression eval (see RESULTS.md) showed:
- The `@{VAR}` hook infrastructure is correct and working
- Prompt-based instruction (SKILL.md) gets ~57% adoption with +3-4 extra overhead turns
- Theoretical ceiling with perfect adoption + zero skill cost: **~54% input token reduction**
  - ~25pp from shorter command strings (`@{REPO}`, `@{TEST_CMD}`)
  - ~29pp from eliminating SKILL.md system prompt overhead
- The gap is entirely in the instruction-following layer — LoRA closes it

## Training Data Synthesis Plan

### What the model needs to learn

The target behavior is a model that:
1. Writes `@{REPO}` instead of a full path on **every** command that contains it — not just the first few
2. Writes `@{TEST_CMD}` or `@{TESTS}` for repeated pytest invocations
3. Uses `@{LastOutput}` and `@{LastCommand[n]}` built-ins without being told
4. Makes **zero** extra management turns (no `macro-set` exploration, no fallbacks to raw paths)
5. Behaves identically to baseline on tasks where no repetition occurs (no false positives)

### Data synthesis approach

Two complementary sources of training examples:

#### Source A: Trajectory rewriting (automated, high volume)

Take existing SWE-bench Lite baseline trajectories (already generated by swe_runner.py) and
mechanically rewrite them into ideal macro-using equivalents.

Steps:
1. Run baseline condition across a larger SWE-bench sample (50-100 tasks, passing only)
2. For each passing trajectory, extract the bash command sequence
3. Identify the tmpdir repo path (regex: `/\S+/swe_[^/\s]+/\w+`)
4. Rewrite every command replacing the path with `@{REPO}`, pytest invocations with `@{TEST_CMD}`,
   and wherever `@{LastOutput}` would be more natural than a re-run, use that
5. Wrap each (original, rewritten) pair as a complete conversation turn in Qwen2.5 chat format
6. Keep only examples where at least 3 substitutions occur (otherwise the signal is too weak)
7. Validate: the rewritten commands, when expanded by session_state.expand(), produce exactly
   the original commands

Output: ~500-2000 high-quality rewrite pairs from SWE-bench tasks alone.

#### Source B: Synthetic scaffolded examples (hand-crafted templates, low volume but high precision)

For behaviors that don't emerge naturally from SWE-bench trajectories (built-in vars, edge cases),
generate synthetic conversation examples covering:

- `@{LastOutput}` to pipe output from one command into the next without re-running
- `@{LastCommand[1]}` to retry the most recent command with a flag added
- `@{PWD}` to navigate relative to current location after a `cd`
- `@{TaskRoot}` to return to the starting directory
- Mixed sessions where some vars are defined midway (agent sets `@{BRANCH}` after checkout)
- Negative examples: tasks with only 1-2 calls where no var should be defined (teach the 3-use heuristic)

Target: ~200-500 hand-crafted examples covering edge cases and built-in vars.

#### Source C: Data augmentation on Source A

- Path length variation: generate examples where the repo path is short (10 chars) vs very long
  (120 chars), to ensure the model's behavior isn't path-length-dependent
- Repo name variation: requests, pytest, django, sympy, flask — vary the leaf dir name
- Mixed-macro examples: `@{REPO}` + `@{TEST_CMD}` + `@{TESTS}` all used in the same session
- Failure recovery: session where an undefined var is caught (hook returns MacroError), and the
  model correctly responds by defining the var and retrying

Target: 2x augmentation of Source A → 1000-4000 total examples.

### Training data format

Each example is a complete multi-turn conversation in Qwen2.5-Instruct chat template format:

```
<|im_start|>system
You are an expert software engineering assistant. You fix bugs in real GitHub repositories.
When working in a repository, use @{REPO} instead of the full directory path in every bash
command. Use @{TEST_CMD} for repeated test invocations. Use @{LastOutput} to reference the
output of the previous command without re-running it.<|im_end|>
<|im_start|>user
You are fixing a bug in psf/requests. Repository: /tmp/swe_psf__requests-2148_abc123/requests
...problem statement...<|im_end|>
<|im_start|>assistant
<tool_call>{"name": "Bash", "arguments": {"command": "cd @{REPO} && grep -n ..."}}</tool_call>
<|im_end|>
<|im_start|>tool
... output ...<|im_end|>
<|im_start|>assistant
...reasoning + next tool call using @{REPO}...<|im_end|>
...
```

Loss masking: compute loss only on assistant turns (reasoning + tool calls). Mask system,
user, and tool result turns.

### Data quality filters

Before including an example:
1. The baseline trajectory must have passed the FAIL_TO_PASS tests (success=true)
2. The rewritten trajectory must be syntactically valid bash when expanded
3. At least 3 `@{VAR}` substitutions must occur
4. The session must have 4+ bash calls (short sessions don't teach the pattern well)
5. No `macro-set` or `macro-list` commands in the rewritten trajectory (those are a crutch)

### Total data target

| Source | Examples | Notes |
|---|---|---|
| A: Trajectory rewrites | 500-2000 | From SWE-bench Lite passing tasks |
| B: Synthetic hand-crafted | 200-500 | Built-ins, edge cases, negatives |
| C: Augmented variants | 1000-4000 | Path length, repo name, mixed-macro |
| **Total** | **~2000-6000** | Aim for 3000 high-quality examples |

Mix in 10-20% general coding SFT data (e.g. OSS-Instruct / CodeAlpaca subset) to
prevent catastrophic forgetting of general coding ability.

## Evaluation Plan

### Primary metric: macro adoption rate on held-out SWE-bench tasks

For each task in a held-out eval set (20-30 tasks not seen in training):
- Run the fine-tuned model with the hook active but no SKILL.md
- Measure: `@{REPO}` uses / eligible path occurrences in baseline (target: >90%)
- Measure: extra turns vs baseline (target: 0 — no management overhead)
- Measure: task pass rate vs baseline (target: equal or better)

### Secondary metric: token savings vs baseline

Compare input tokens per session between:
- Baseline (original Qwen2.5-Coder-32B, no macro)
- Fine-tuned model (no SKILL.md, macro hook active)

Target: >40% reduction (leaves room for incomplete adoption while still being useful).

### Regression tests

- General code benchmark (HumanEval, MBPP): fine-tuned must score within 2% of base
- Tasks with no repetition: fine-tuned must not insert spurious `@{REPO}` references
  (false positive rate target: <5%)

## Milestones

1. **Data pipeline** — script that takes swe_runner.py logs → rewrites trajectories →
   outputs JSONL in Qwen chat format. Target: 1-2 days.
2. **Data generation** — run baseline on 80-100 SWE-bench tasks (passing only), rewrite,
   augment. Target: 500-2000 examples in 1-2 days.
3. **First training run** — axolotl or unsloth on A100 80GB, Source A only, 3 epochs.
   Checkpoint at epoch 1 and 2. Target: 1 day.
4. **Eval loop** — run fine-tuned model on held-out set, measure adoption + token savings.
   Target: 1 day.
5. **Iterate** — add Source B/C data, adjust LoRA rank, retrain. 2-3 iterations expected.
6. **Final eval** — full held-out set, compare vs baseline + prompt-based SKILL.md baseline.

## Open Questions

- Does Qwen2.5-Coder-32B have enough base SWE-bench capability to make the fine-tune
  worthwhile? If it can only solve 15-20% of tasks on its own, the macro savings matter
  less. First training run will clarify.
- How many training examples are needed before adoption reliably reaches >80%?
  Hypothesis: 500 high-quality rewrites is enough; will test at 200, 500, 2000.
- Does LoRA on tool-use format work better with axolotl (more config control) or
  unsloth (faster, less memory)? Start with unsloth for speed; switch to axolotl
  if chat template handling is problematic.
- Should negative examples (tasks where no macro is warranted) be included, and
  at what ratio? Too many negatives may suppress adoption; too few may cause
  false positives on short sessions.
